# Decompile

Two different things are called "the decompile" in this repo:

- **Ghidra's C** (`decompiled/`, local only, never committed): the whole game as readable C with our names and types, for
  reading and searching ([workflows.md](workflows.md#5-read-and-search-the-code)). Made by `tools/rebuild_decomp.ps1` /
  `tools/rebuild_decomp.sh` inside the full run (`pwsh tools\batches\run_all.ps1` / `tools/batches/run_all.sh`).
- **The Phase 4 build** (`decomp/`, a decomp-toolkit project): `main.dol` rebuilt from dtk's split objects, with the
  objects that have matching C compiled from `decomp/src` (committed), checked against the retail SHA-1 by batch 9.
  See "Building library objects from C" below, [REPRODUCE.md](REPRODUCE.md) section 2b, [compiler.md](compiler.md) and
  [drafts.md](drafts.md).

How the full run orders the name batches, the Ghidra rebuild and the checks: [REPRODUCE.md](REPRODUCE.md), section 2.

## Pipeline (`tools\rebuild_decomp.ps1`)

`tools/rebuild_decomp.sh` does the same on Linux / macOS.

1. `analyzeHeadless` imports `Custom Robo extracted/sys/main.dol` with the GameCube loader (`-loader GameCubeLoader -loader-autoloadMaps false`).
2. Pre-script `EnableGCAnalyzer.java` turns on the loader's "(GameCube/Wii) Program Analyzer", which sets r13 = 0x804543C0 and r2 = 0x804581A0 (small-data bases). It is off by default because its enablement check compares the program format with "Nintendo GameCube/Wii Binary" while the loader now reports "Nintendo GameCube/Wii Binary (Executable)" — **verified**: enabling it took `unaff_r13` from 22,062 to 0.
3. Post-scripts, in order: `CreateDtkFunctions.java` (function starts dtk found), `ApplySymbols.java symbols/symbols.txt`,
   `ApplySymbols.java symbols/descriptive.txt`, `DefineStrings.java`, `ParseHeaders.java` (types, prototypes, globals ->
   `symbols/types_report.txt`), `ExportXrefs.java` (`decompiled/xrefs/`), `ExportDecompiledC.java decompiled/main_dol.c`.
   Each script: [tools.md](tools.md#ghidra-scripts-toolsscripts).

## Naming policy

The full, current policy (rules 1-6 and R7 / R8 from the matched C, plus the cross-check of every name on every run) is
in [plan.md, "Naming policy"](../plan.md#naming-policy-applies-to-symbolssymbolstxt); how to add a name:
[CONTRIBUTING.md](../CONTRIBUTING.md). In short, a name goes into `symbols/symbols.txt` only with an independent
source: a decomp-toolkit signature match; a Melee assert match with the size within 10%; layout proof between verified
anchors (`tools/layout_match.py`, batch 1); asserts, call graph or a unique string against the reference decomps
(batch 6); or the matched C's call sites / definitions (R7 / R8, checked by `tools/check_c_callsites.py` in batch 9).
Batch 8 (`tools/crosscheck_names.py`) re-checks every name with evidence other than the rule that produced it and stops
the run on any FAIL ([names_crosscheck.md](names_crosscheck.md); last run: 2,381 names, 0 FAIL).

Before rejecting a name for "not in Melee's symbols", search all of Melee (`config` + `src`): a `static` / `inline` function is folded into its caller and never appears on its own. Then check the caller instead.

Descriptive guesses go to `symbols/unverified.txt` (never applied). The report of the last check is `symbols/verify_report.txt`.
The first name set (Oct 25, 2026: 298 dtk signatures, 46 Melee asserts, 4 layout proofs) and what was rejected then:
plan.md steps 9-11 and "First decompile results".

### Types

Library structs and prototypes come from Melee's headers (`ParseHeaders.java`), checked three ways: the headers' own ASSERT_SIZE lines, their `/* +XX */` field offsets, and the object sizes Custom Robo registers for each HSD class (`tools/check_class_sizes.py`). Custom Robo's differences are overrides in `tools/clean_headers.py`. Our own types: `symbols/cr_types.h`, globals: `symbols/cr_globals.txt`. Report: `symbols/types_report.txt`. How to add one: [CONTRIBUTING.md](../CONTRIBUTING.md#types-struct-fields-parameters-and-globals). plan.md step 23.

### Character objects

`cr_Chara` (0x19A8 bytes, 24 in `cr_g_Charas` at 0x803BFE88; `cr_g_CurrentChara` points at the one being processed) is a
**story-mode field character**, not the battle robo: its motions are walk / run / talk_* / battle_in (the game's own
names), scripts and area boxes drive it (plan.md steps 39-41; the struct was first read as the robo in play). Known
fields and their evidence: `symbols/cr_types.h`; plan.md steps 30-38. The four robos in battle are a separate array at
0x8024E120 + n × 0x33520 (community lead, [community/codes_addresses.md](community/codes_addresses.md); not in our types yet).

### Real-name evidence

`tools/name_evidence.py` lists every name the game itself still holds (enum name tables, identifier strings, debug formats, source files) with the code that uses them: [name_evidence.md](name_evidence.md), [name_tables.tsv](name_tables.tsv). Rule: use these before any `cr_` name ([CONTRIBUTING.md](../CONTRIBUTING.md#real-names-first)). Batch 7 applies the ones it can prove (`tools/match_game_names.py`, plan.md step 48). The motion name table (0x80206DB0) gives the motion IDs their real names (plan.md steps 40, 46).

### Game sequences

The game runs one sequence at a time (`cr_Seq`: SEQ_LOGO, SEQ_MOVIE, SEQ_TITLE, SEQ_FIELD, SEQ_BATTLE, ... - the game's own names). `cr_g_SeqCurrent` (a `cr_SeqState`, 0x48 bytes: current / previous / next sequence and the handlers' counters, step 77) picks the handlers in five tables: `cr_g_SeqEnter` / `cr_g_SeqLeave` on a change, `cr_g_SeqFrameA/B/C` every frame. Handlers are named `cr_SEQ_BATTLE_Enter` etc. To find a mode's code, start at its handlers. plan.md step 42.

### Script commands

The game's script interpreter dispatches through `cr_g_ScrCmdFuncs` (0x8021C3F4, 300 handlers), indexed by command number; the matching names (`SYS_SET_SCR`, ... ) are in `cr_g_ScrCmdNames` (0x8021BF44), directly before it. Handlers are named `cr_<COMMAND NAME>`. plan.md step 44.

### Camera modes

`cr_Cam_SetMode` (0x80024830) writes the mode to byte 0 of the current camera; the 18 `CAMMODE_*` names (table 0x801F88A4) name the per-mode handlers (`cr_CAMMODE_MIDDLE_Frame` ...). plan.md steps 43, 45.

How to add a C file (one object of `decomp/config/GXCE01/splits.txt`):
Python tools are named by script only; run them with `python -I` (Windows) or `python3 -I` (Linux / macOS).

1. Copy it with its headers, never by hand:
   `tools/import_ref_source.py <ref> <path in ref> src/<object path> --inc <ref include dir>=include/<ref> ...`
   - SDK: `dolsdk2004 src/os/OSCache.c src/dolphin/os/OSCache.c --inc include=include/dolsdk2004 --inc include/libc=include/dolsdk2004/libc`
   - MSL / Runtime / TRK: `marioparty4 src/MSL_C.PPCEABI.bare.H/mem.c src/MSL/mem.c --inc include=include/marioparty4`

   The provenance comment goes on line 1 (same line), so line numbers stay the reference's.
2. `cd decomp; python configure.py; ..\tools\ninja\ninja.exe` (Windows) or
   `cd decomp && python3 configure.py && ../tools/ninja/ninja` (Linux / macOS) compiles it (for objdiff only); then
   `tools/check_c_objects.py --link-each` links the build with it taken from C: `retail` = it can be linked.
   The check stops until the file is listed: in `CR_NOT_MATCHING` (decomp/configure.py) with its reason, or in
   `CR_MATCHING`.
3. If functions differ, adapt the source (objdiff GUI on `decomp/`, or `objdiff-cli diff -p decomp -u main/<object> -o -`,
   the object's path without `.c`, e.g. `main/sysdolphin/baselib/lobj`; the unit names are in `decomp/objdiff.json`).
   A `fn_...` at 0% usually exists in the C under its real name (the link test shows it).
   If the link fails on an undefined name (the C calls / uses something our symbols leave as `fn_` / `lbl_`):
   `decomp/reports/c_callsites_report.txt` (`tools/check_c_callsites.py`, batch 9) lists every name the matched C's
   call sites give to a dtk default name, with its address (`UNNAMED` lines). Add it to `symbols/symbols.txt` in the
   "Matched-C call sites" block, tagged `// c-callsite obj:<C file> at:<function>+0x<offset>`, with `ref_size:` and a
   `why:` (reference size, place in the reference file); batch 9 re-derives it every run and stops if it disagrees.
   Not when another C object linked from C defines that name (it would be defined twice): that is a data split.
   A global of the C file itself that another object uses but no matched function calls by name (rule R8): when
   the file matches its whole object, `decomp/reports/splits_report.txt` lists where it defines it (`DEF` lines);
   add it in the "Matched-C definitions" block, tagged `// c-define obj:<C file> ref_size:`, with a `why:`.
   The object's data pieces come from the C itself (`tools/gen_dtk_splits.py`, step 56): a C file that matches
   every function of its object proves where its data is, so nothing is placed by hand.
   **Trailing padding** (step 61 iteration 8): a C piece ends at the C's own last byte. When only zeros follow up to
   another object's piece that starts at the first address after it aligned to that object's alignment (dtk's split
   alignment: the largest `align:` of its symbols, else 8; from C, also its .o section's), the zeros are that
   object's alignment: the linker makes them (asm: its `.balign`; C: its section alignment) and dtk makes no
   automatic object of a gap shorter than the next split's alignment. Otherwise the zeros stay with the C piece (up
   to the next piece or the section end), or, before a dtk automatic object, start that object from the next word
   (an automatic object must start 4-aligned, so a C piece ending at an odd byte keeps up to 3 zeros and objdiff
   reports its section short: name / split the next object, as perf.c after fog.c). A dtk symbol that runs on over
   the C's last byte is cut there in config symbols.txt (`trim_symbols`; a split may not end inside a symbol). The
   zeros after a C piece placed earlier (in path order) also count as that piece's when the next C file asks whether
   one of its stripped globals could be in front of its piece.
   Second pass: the relocation users' data pieces are computed again bounded by the C pieces (a symbol next to a
   candidate range that lies in another object's C piece is that object's, whoever uses it), then the C pieces again
   (video.c's .data after initialize.c's).
4. In `CR_MATCHING`: `tools/make_configure_patch.py`, then batch 9. `tools/gen_c_symbols.py` gives the object
   the C's own symbols (objdiff pairs data by name), `tools/check_c_objects.py` must report 100% code + data, main.dol

### Game file objects (step 63, Oct 30, 2026)

The game code has no reference decomp, so its object edges come from the code itself. Linked game functions are
one object each (`decomp/src/game/<function>.c`) as long as they own no data. A function that uses a compiler
constant (.sdata2: float literals, the int-to-float double) or a string literal can only be linked with the rest of
its source file, because that data is the file's own pool:
- **the per-file pool rule** (tools/gen_dtk_splits.py, already used for library edges): every source file
  has its own .sdata2 constant pool and string literals, laid out in link order. The game confirms it: 0.0f is in
  .sdata2 41 times, the two int-to-float doubles 28 and 26 times (one copy per file).
- **the file run**: every function that uses one of a function's pool entries is in its file, and so is every
  function between them (a file's code is contiguous); repeated until closed (tools/promote_drafts.py `Pools`).
- **a file object** `game/<first>_<last>.c` is made when every function of the run is a 100% draft: the drafts one
  after another in one generated file. It must compile to the drafts' .text in a row, and its own data must sit in
  main.dol exactly once: every relocation into its .sdata2 / strings gives the same piece start, the bytes are
  main.dol's, and no code or data outside the run uses the piece (`gen_dtk_splits.game_file_data`, which also adds
  the piece to splits.txt). The run's one-function files are removed.
- When a pool entry is also used by a function that is not matched yet, the run cannot be built yet. The entry stays
  in dtk's automatic object and the functions keep their own objects.
  `decomp/reports/promote_report.txt` ("file runs") lists each run, how many of its functions match, and the span of
  each draft's direct pool users.

### Game data objects (step 86, Oct 31, 2026)

The third kind of game unit (tools/gen_dtk_splits.py, docstring "GAME code" item 3): a C file in `decomp/src/game/data/`
that defines data objects and no code. Its bytes are the game's data, generated, not typed: `tools/gen_data_c.py` takes
globals of `symbols/cr_globals.txt` (name, section, address, `cr_types.h` type), writes their definitions (for
.data / .sdata / .rodata / .sdata2 an initialiser from main.dol's bytes, element by element along the type: numbers,
the shortest float literal with the same bits, pointers as the name of ours at the relocation target, function pointers
as the function's name; .bss / .sbss zero), compiles the file with the game flags and places it with the same rule batch
9 uses (`gen_dtk_splits.data_unit_pieces`): every defined symbol is one of ours at its address, the symbols of one
section sit at the object's distances (one piece start per section), the piece starts on a dtk symbol start, the
bytes equal main.dol's with every relocated word going where main.elf relocates it, and it ends at the C's last byte
(the next dtk symbol starts there, or only zeros follow: the trailing-padding rule of step 65). Only a file that
passes is written. `tools/gen_c_symbols.py` then gives the unit its own symbols, objdiff must report 100% data, main.dol
stays retail, and `tools/shift_test.py` pads at the start of every unit that is not inside a glue span (below).

**How to add one.** Pick globals that are contiguous in main.dol (the next starts where the previous ends), typed in
`symbols/cr_types.h` with dtk's object size (or a size dtk's symbols can be cut / merged to, below), in one section:
`python -I tools/gen_data_c.py NAME [NAME ...]` writes `decomp/src/game/data/<first>_<last>.c` (`--check` only
verifies); add the list to `UNITS` in the tool (so `--all` regenerates it after a type or name change), run batch 9
(retail SHA-1, every C object 100%, relocations OK, static shift PASS), then batch 11 (the shifted build boots).
A unit is never edited by hand; after a rename in `symbols/` batch 9's `sync_game_names.py` renames the identifiers,
and a type change means regenerating (`--all`). The drafts' context (`decomp/drafts/ctx_pp.c`, batch 12) must exist.

**Rules found (GC/2.6 with the game flags).**
- The compiler lays `.data` / `.sdata` / `.rodata` / `.sdata2` out in declaration order and `.bss` / `.sbss` in REVERSE
  declaration order (measured; step 83 saw the .bss half), with natural alignment between the objects; a global of 8
  bytes or less goes to the small-data section whatever the file says (`-sdata 8 -sdata2 8`). The generated file orders
  its definitions accordingly.
- Every section of the compiled object is 8-aligned (`-align powerpc`), so a unit's piece must start 8-aligned: a
  typed global at a 4-aligned address (cr_g_StageSelector 0x8041A244, cr_g_Customize 0x8041CDE4, cr_g_FileSlots
  0x80320184, cr_g_ScrCmdNames 0x8021BF44, cr_g_PartOrderBody 0x8023B73A) can only come with the untyped object before it.
- dtk's symbol sizes are not the types': the C's size wins when the difference is mechanical. dtk saw cr_g_Pads as
  three objects (0x14 + 0x8 + 0x274 = one `cr_Pad[4]`) and cr_g_BattleMotionSets as 34 objects of 0x4C: the default
  `lbl_` symbols inside the C's object are dropped from the config `symbols.txt` and the first takes the C's size
  (`SYM_DROP` / `SYM_TRIM`; the first link already needs that layout, before `gen_c_symbols.py` runs). dtk's
  cr_g_FileDescs was 0xC0 = the 43 pointers + 0x14 zero bytes: the C has 43, the zeros start an automatic object
  (step 65's rule). A dtk object that runs on into OTHER data blocks the unit: cr_g_CamModeFuncs (dtk 0xE0, the 42
  pointers then 14 floats), cr_g_CharaMotionSets (0x19C vs 0xE0), the SEQ handler tables (cr_g_SeqFrameA 0x78 holds
  cr_g_SeqNames; cr_g_SeqFrameC 0xCBC runs to 0x801DF7E8) - a symbol split with evidence for the rest is the lever.
- A table of strings needs the file's own string pool: with `-str reuse,readonly` the compiler puts a `char *` table's
  literals into the unit's .rodata (longer than 8 bytes; shorter ones into .sdata2), so the strings must be contiguous
  in main.dol and used by nothing else. cr_g_SeqNames' 15 strings open .rodata (0x801B6620) but the code uses

  string pool, a pointer into the middle of a symbol, a pointer slot holding a number, a union or a bit field.
- **Glue spans are the game's data pools.** `tools/reloc_audit.py`'s glue spans (constant-offset arithmetic from one
  dtk object into another) are 89 ranges of game data; 0x803B8C00..0x803E66B4 (0x2DAB4 bytes of .bss) is addressed from
  the one base lbl_803B8C00 by 2,674 accesses in 62 functions (fn_800A0E64 309, cr_AreaBoxes_Update 156,
  cr_Chara_UpdateAll 133, cr_CM_PLAYER_RESET, cr_SYS_RET, cr_MAP_SET ...), while 280 other functions address
  cr_g_Script by its own symbol: the 62 are the file that DEFINES the data, and CodeWarrior addresses a file's own data
  from one base (its data pool), other files' data by symbol. A unit inside a glue span is byte-identical and links,
  but it can only move together with that file's whole data (dtk's relocations of the 62 functions name the base, not
  the unit's symbols); `shift_test.py` refuses points inside a span, as before. Outside a span every reference to the
  unit is a relocation to its symbols, and the shift test now pads at each such unit's start (7 of the 14).
  Consequence for the end state: a file's data definitions must live in the file with its code (compiled, the pool
  comes back as base + offsets); the data units are the interim form that proves the types and the bytes.
