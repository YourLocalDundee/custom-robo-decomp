# Decompile

Two different things are called "the decompile" in this repo:

- **Ghidra's C** (`decompiled\`, local only, never committed): the whole game as readable C with our names and types, for
  reading and searching. Made by `tools\rebuild_decomp.ps1` inside `run_all.ps1`.
- **The Phase 4 build** (`decomp\`, a decomp-toolkit project): `main.dol` rebuilt from dtk's split objects, with the
  objects that have matching C compiled from `decomp\src` (committed), checked against the retail SHA-1 by batch 9.
  See "Building library objects from C" below, [REPRODUCE.md](REPRODUCE.md) section 2b and [drafts.md](drafts.md).

## Pipeline (`tools\rebuild_decomp.ps1`)

1. `analyzeHeadless` imports `Custom Robo extracted\sys\main.dol` with the GameCube loader (`-loader GameCubeLoader -loader-autoloadMaps false`).
2. Pre-script `EnableGCAnalyzer.java` turns on the loader's "(GameCube/Wii) Program Analyzer", which sets r13 = 0x804543C0 and r2 = 0x804581A0 (small-data bases). It is off by default because its enablement check compares the program format with "Nintendo GameCube/Wii Binary" while the loader now reports "Nintendo GameCube/Wii Binary (Executable)" — **verified**: enabling it took `unaff_r13` from 22,062 to 0.
3. Post-scripts, in order: `CreateDtkFunctions.java` (function starts dtk found), `ApplySymbols.java symbols\symbols.txt`,
   `ApplySymbols.java symbols\descriptive.txt`, `DefineStrings.java`, `ParseHeaders.java` (types, prototypes, globals ->
   `symbols\types_report.txt`), `ExportXrefs.java` (`decompiled\xrefs\`), `ExportDecompiledC.java decompiled\main_dol.c`.
   Each script: [tools.md](tools.md), "Ghidra scripts".

## Naming policy

The full, current policy (rules 1-6 and R7 / R8 from the matched C, plus the cross-check of every name on every run) is
in [plan.md, "Naming policy"](../plan.md#naming-policy-applies-to-symbolssymbolstxt). In short, a name goes into
`symbols\symbols.txt` only with an independent source: a decomp-toolkit signature match; a Melee assert match with the
size within 10%; layout proof between verified anchors (`tools\layout_match.py`, batch 1); asserts, call graph or a
unique string against the reference decomps (batch 6); or the matched C's call sites / definitions (R7 / R8, checked
by `tools\check_c_callsites.py` in batch 9). Batch 8 (`tools\crosscheck_names.py`) re-checks every name with evidence
other than the rule that produced it and stops the run on any FAIL ([names_crosscheck.md](names_crosscheck.md)).

Before rejecting a name for "not in Melee's symbols", search all of Melee (`config` + `src`): a `static` / `inline` function is folded into its caller and never appears on its own. Then check the caller instead.

Descriptive guesses go to `symbols\unverified.txt` (never applied). The report of the last check is `symbols\verify_report.txt`.

## Batch pipeline and search (Oct 27, 2026; updated Oct 29)

`pwsh tools\batches\run_all.ps1` (about 17 min in all; about 4 min per Ghidra rebuild + name pass: 1 rebuild with an export present, 2 on a fresh setup; `-SkipRebuild` to reuse the current Ghidra output) runs:
batch 1 layout-proof names (`tools\layout_match.py`) + batch 6 lib candidates + batch 7 the game's own names (`tools\match_game_names.py`, plan.md step 48) + lint ->
Ghidra rebuild (also `CreateDtkFunctions.java`, `ExportXrefs.java`) -> batches 1 + 6 + 7 again, rebuilding until no name file changes (plan.md step 47) -> batch 5 types -> batch 2 dtk cross-check (`symbols\crosscheck_report.txt`) ->
batch 3 game map (`docs\game_map.md`) -> batch 4 search index (`decompiled\index.db`, `decompiled\funcs\`) -> batch 8 name cross-check (`docs\names_crosscheck.md`; stops on any FAIL) -> batch 9 decomp build (retail SHA-1, relocations, static shift test)
-> batch 10 compiler probe -> batch 11 shifted build booted in Dolphin (don't type or click while Dolphin is open) -> batch 12 m2c drafts of the game code ([drafts.md](drafts.md)) + `tools\promote_drafts.py` into `decomp\src\game` (batch 9 again when that changed) -> `tools\checksums.ps1 -Compare`. One script runs it all, in order, stopping at the first failure.

Search examples:
```
python -I tools\find.py text chara_bin          full-text over all C
python -I tools\find.py func 800747b0           print one function (address or name)
python -I tools\find.py callers 800747b0        direct calls + places that take its address
python -I tools\find.py refs 801F1200           every instruction touching an address
python -I tools\find.py str snr_motion          strings + the functions using them
python -I tools\find.py hint anim               game functions reaching animation code
```

## Types (Oct 27, 2026)

Library structs and prototypes come from Melee's headers (`ParseHeaders.java`), checked three ways: the headers' own ASSERT_SIZE lines, their `/* +XX */` field offsets, and the object sizes Custom Robo registers for each HSD class (`tools/check_class_sizes.py`). Custom Robo's differences are overrides in `tools/clean_headers.py`. Our own types: `symbols/cr_types.h`, globals: `symbols/cr_globals.txt`. Report: `symbols/types_report.txt`. Details: plan.md step 23.

## Robo objects (Oct 27, 2026)

`cr_Chara` (0x19A8 bytes, 24 in `cr_g_Charas` at 0x803BFE88) is the robo in play; `cr_g_CurrentChara` points at the one being processed. Known fields and their evidence are in `symbols/cr_types.h`; plan.md step 30.

## Real-name evidence (Oct 27, 2026)

`tools/name_evidence.py` lists every name the game itself still holds (enum name tables, identifier strings, debug formats, source files) with the code that uses them: `docs/name_evidence.md`, `docs/name_tables.tsv`. Rule: use these before any `cr_` name (CONTRIBUTING.md). First result: the motion name table (0x80206DB0) gives the 17 field-character motion slots their real names (plan.md step 40).

## Game sequences (Oct 27, 2026)

The game runs one sequence at a time (`cr_Seq`: SEQ_LOGO, SEQ_MOVIE, SEQ_TITLE, SEQ_FIELD, SEQ_BATTLE, ... - the game's own names). `cr_g_SeqCurrent` picks the handlers in five tables: `cr_g_SeqEnter` / `cr_g_SeqLeave` on a change, `cr_g_SeqFrameA/B/C` every frame. Handlers are named `cr_SEQ_BATTLE_Enter` etc. To find a mode's code, start at its handlers. plan.md step 42.

## Script commands (Oct 28, 2026)

The game's script interpreter dispatches through `cr_g_ScrCmdFuncs` (0x8021C3F4, 300 handlers), indexed by command number; the matching names (`SYS_SET_SCR`, ... ) are in `cr_g_ScrCmdNames` (0x8021BF44), directly before it. Handlers are named `cr_<COMMAND NAME>`. plan.md step 44.

## Building library objects from C (Phase 4 Milestone 4, Oct 29, 2026)

Not the Ghidra C above (that is never copied anywhere): the community's own matching C from the pinned reference
decomps, compiled by the Phase 4 build (`decomp/`). Status: `decomp/reports/progress_report.txt` (Oct 29, 2026: 92
library objects from C, 44 more C files in `decomp/src` compiled for objdiff only, each with its reason in
`CR_NOT_MATCHING`); provenance of every file: `decomp/reports/sources_report.txt`. Game functions come into
`decomp/src/game` another way (m2c drafts that match, promoted by script): [drafts.md](drafts.md).

How to add a C file (one object of `decomp/config/GXCE01/splits.txt`):
1. Copy it with its headers, never by hand:
   `python -I tools/import_ref_source.py <ref> <path in ref> src/<object path> --inc <ref include dir>=include/<ref> ...`
   - SDK: `dolsdk2004 src/os/OSCache.c src/dolphin/os/OSCache.c --inc include=include/dolsdk2004 --inc include/libc=include/dolsdk2004/libc`
   - MSL / Runtime / TRK: `marioparty4 src/MSL_C.PPCEABI.bare.H/mem.c src/MSL/mem.c --inc include=include/marioparty4`
   - HSD: `melee src/sysdolphin/baselib/util.c src/sysdolphin/baselib/util.c --inc src=src --inc libs/doldecomp/include=include/melee/doldecomp --inc src/MSL=include/melee/MSL --inc libs/dolphin/include=include/melee/dolphin`
   The provenance comment goes on line 1 (same line), so line numbers stay the reference's.
2. `cd decomp; python configure.py; ..\tools\ninja\ninja.exe` compiles it (for objdiff only); then
   `python -I tools\check_c_objects.py --link-each` links the build with it taken from C: `retail` = it can be linked.
   The check stops until the file is listed: in `CR_NOT_MATCHING` (decomp/configure.py) with its reason, or in
   `CR_MATCHING`.
3. If functions differ, adapt the source (objdiff GUI on `decomp/`, or `objdiff-cli diff -p decomp -u main/<object>`).
   A `fn_...` at 0% usually exists in the C under its real name (the link test shows it).
   If the link fails on an undefined name (the C calls / uses something our symbols leave as `fn_` / `lbl_`):
   `decomp/reports/c_callsites_report.txt` (`tools/check_c_callsites.py`, batch 9) lists every name the matched C's
   call sites give to a dtk default name, with its address (`UNNAMED` lines). Add it to `symbols/symbols.txt` in the
   "Matched-C call sites" block, tagged `// c-callsite obj:<C file> at:<function>+0x<offset>`, with `ref_size:` and a
   `why:` (reference size, place in the reference file); batch 9 re-derives it every run and stops if it disagrees.
   Not when another C object linked from C defines that name (it would be defined twice): that is a data split.
   A global of the C file itself that another object uses but no matched function calls by name (rule R8): when
   the file matches its whole object, `decomp/reports/splits_report.txt` lists where it defines it (`DEF` lines);
   add it in the "Matched-C definitions" block, tagged `// c-define obj:<C file> ref_size:`, with a `why:`.
   The object's data pieces come from the C itself (`tools/gen_dtk_splits.py`, step 56): a C file that matches
   every function of its object proves where its data is, so nothing is placed by hand.
4. In `CR_MATCHING`: `python -I tools\make_configure_patch.py`, then batch 9. `tools/gen_c_symbols.py` gives the object
   the C's own symbols (objdiff pairs data by name), `tools/check_c_objects.py` must report 100% code + data, main.dol
   must stay retail. Then the full `run_all.ps1`, and `checksums.ps1 -Write` for the intended changes.

### HSD (sysdolphin) notes (step 61, Oct 30, 2026)

- Custom Robo links the Kirby Air Ride revision of sysdolphin (tools/refs/kar, kar_wowjinxy: the same function sizes),
  newer than Melee's. Differences that matter for importing Melee's C: every `*Info` class struct has one more
  method than Melee's (`tools/check_class_sizes.py`: HSD_JObjInfo 0x54 vs 0x50 ...), the `*GetAllocData` and flag
  accessors are inlined or absent (dobj.c 16 functions here vs 19 in Melee), some functions are larger
  (HSD_SetupChannel 0x3A4 vs 0x32C, HSD_ObjAllocInit 0x124 vs 0xE0).
- Object edges (`tools/gen_dtk_splits.py`): the HSD objects are split from Melee's splits.txt once their first / last
  function and the neighbour across the edge are named. `HSD_ObjInit` (initialize.c) calls the ten `*InitAllocData`
  functions, the first function of list.c, aobj.c, robj.c, tev.c, displayfunc.c and the last of mtx.c, so it named
  nine edges at once (symbols/symbols.txt, "HSD object edges" block). A named function another reference places in
  the same file (a header inline's out-of-line copy such as HSD_JObjRef, or a function of the newer revision) does
  not break a range. What still blocks each file is listed in `decomp/reports/splits_report.txt`
  (`GALE01:sysdolphin/...` lines).
- Function count (gen_dtk_splits.py rule 5, iteration 2 of step 61): a count BELOW the reference's by more than
  max(2, 25%) is accepted when both edges are named neighbours that the reference puts in other files (rule 4's
  "the named function next to it is another object's"), never on pools, size runs, asserts or the section edge alone;
  a count above is still rejected. The report's header line "accepted with fewer functions than the reference" lists
  every object for which some proving reference needed it (in HSD: aobj, class, cobj, fobj, jobj (KAR's count), lobj,
  pobj, robj, video; the MSL / SDK names there were already split by another reference and are unchanged). For HSD
  objects only, a named neighbour the reference does not have and that no reference or pinned source puts in the
  object's file counts as an unnamed one, so naming a newer revision's function (HSD_SaveContext after texpdag.c)
  loses no proof.
- Names that unblocked edges (symbols/symbols.txt "HSD object edges", each with its `why:`; batch 8: 0 FAIL):
  HSD_IDGetDataFromTable (id.c / wobj.c), HSD_CObjEraseScreen (lobj.c / cobj.c; the wowjinxy map's
  HSD_CObjSetViewportScale is not used), HSD_HashSearch (class.c / hash.c), splGetHelmite (video.c), and
  HSD_Alloc, HSD_ArchiveGetPublicAddress, HSD_SaveContext (their bodies equal doldecomp/kar's asm or C; they do not
  unblock shadow.c / archive.c / debug.c yet, see plan.md).
- C from Kirby Air Ride (doldecomp/kar, `REF=kar`): its sources include `<sysdolphin/x.h>` and bare `"x.h"`, so a kar
  object is imported with `--inc src=include/kar --inc include=include/kar` and compiled with its own search path
  (decomp/configure.py `CR_OBJECT_INCLUDES`: `-cwd explicit -i include/cr_kar -i include/kar -i include/kar/sysdolphin
  -i src/sysdolphin/baselib`): `-cwd explicit` keeps the Melee headers next to util.c / object.c in
  src/sysdolphin/baselib from shadowing kar's of the same name. `decomp/include/cr_kar/` holds the Custom Robo
  overrides (found first; the kar copy stays unchanged): sysdolphin/list.h (kar's list.c defines HSD_SListAppend /
  Prepend, our names are Melee's HSD_SListAllocAndAppend / AllocAndPrepend), sysdolphin/wobj.h (kar's class info
  `lbl_805041C8` is `hsdWObj`). A new override header does not rebuild an object compiled before it (ninja's .d file
  does not list it): delete that .o once.
- From C after iteration 2: util.c, object.c (Melee), list.c, id.c (kar), 100% code and data, main.dol retail.
  Whole matches not linked yet (100% code, each function its own by bytes): class.c, dobj.c, wobj.c: they use
  functions / data our symbols do not name yet (memory_list, nb_memory_list, _HSD_MemAlloc; _OSReport,
  HSD_PObjRemoveAnimAll, HSD_MObjAddAnim, HSD_AObjInterpretAnim; HSD_RObjRemoveAll, objInfo): name them from the call
  sites (rule R7). kar's objalloc.c is an unfinished stub (does not compile), not imported. The others imported
  (aobj, fobj, fog, initialize, lobj, mobj, pobj, robj) match 0-95% of their bytes: reasons in `CR_NOT_MATCHING`.
