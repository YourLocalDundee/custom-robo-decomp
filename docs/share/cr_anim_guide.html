Custom Robo animations: formats, playback and tools

Everything known about how Custom Robo (GameCube, US) stores and plays its animations, in one page for modders and tool writers. Each fact is read from the game's code (function addresses given) or checked over every file on the disc; anything not verified says so. Deeper pages: formats/motion.md (file layout), formats/motion_playback.md (what the game does with the tracks), battle_animations.md (which animation plays when).

2The motion file format (verified: byte-identical round trip of all 51 motion files)

All values big-endian.

Boot bundle logo_read_us.dbn: u32 count (9), count + 1 u32 offsets from the file start (the last = file length), zeros to 0x40; entries 0x20-aligned. Entry 8 (the last) is the motion file; the bundle may grow up to 2,842,624 bytes (the load region at boot, fn_80023CBC).

Motion file

WhereWhat
+0u32 group count G (3 in the bundle)
+4G u32 group offsets (from the file start), then the file length, zeros to 0x20
group +0u32 motion count n
group +4n entries of 3 u32 offsets from the group start: tracks, pool, counts
group +4 + 12nn u16 motion IDs; bit 15 set = 78 tracks (every motion on the disc), clear = 69

Per motion:

  • tracks: 78 pairs of u32 offsets (time list, value list); both 0 for a track without keys.
  • counts: one byte per track, its key count.
  • pool: the same offset for every motion of a group: the group's shared float pool (de-duplicated; at most 16,384 floats, the index is 14 bits).

A time list is count u16 frame numbers, starting at 0, non-decreasing (a repeated frame = an instant change); tracks may share time lists. A value list is count u16 key words:

Bits 15-14 (kind)Floats at pool[bits 13-0]Key
0value, in-tangent, out-tangentfull
1 (0x4000)nonevalue 0, flat
2 (0x8000)valueflat tangents
3 (0xC000)value, tangentone tangent both sides

The curve (cr_Motion_SampleTrack 0x8001EB48): between keys at frames t0 and t1, s = (f - t0) / (t1 - t0), dt = (t1 - t0) / 30,

v = p0 (1 - s)^2 (1 + 2s) + p1 s^2 (3 - 2s) + dt (m0 s (1 - s)^2 - m1 s^2 (1 - s))` (cubic Hermite; tangents per

second at 30 frames a second). Before the first key and on a key: the key's value.

Rule: every non-empty track must end on its motion's last frame. Past a track's last key the game reads the following words as more keys (a single-key track broke a battle in a test). Every file on the disc follows this.

Layout details for writers (needed for byte-identical output): the file length after the group offsets; 0xFF fill from the counts to the 4-aligned value lists; time lists right after the value lists, shared when one is the start of another; track tables 4-aligned; groups 0x20-aligned. A motion ID registered by an earlier file wins (cr_MotionFile_Register 0x80074DCC).

3What the 78 tracks mean: an IK rig, not joint rotations (verified from the player code)

TracksChannelUnit
0-2point 0: root point (hips)model units
9-11, 15-17points 1, 2: upper body and head aim targetsmodel units
24-26, 36-38points 3, 4: hand targets (swap when mirrored)model units
48-50, 60-62points 5, 6: foot targets (swap when mirrored)model units
3-8, 12-14, 18-23, 27-35, 39-47, 51-59, 63-68x, y, z rotation of 16 joints of the game's default skeleton: body, upper body, head, arm A shoulder / upper / hand, arm B the same, lower body, leg A thigh / ankle / foot, leg B the samedegrees
69-71root translationmodel units
72-74root rotation x, y, zdegrees
75-77a vector turned by the root rotation, added to the root translationmodel units

Every frame (cr_Chara_PoseFromMotion 0x8003D4C4): root -> blend -> the 7 points through the root matrix and the 16 joint angles -> rotation matrices Rz.Ry.Rx -> the body: upper body and head aimed at points 1 / 2, two-bone IK for each arm and leg toward its point (solved on the game's default skeleton, then rebuilt with this robo's own limb lengths from its model's block A) -> 20 body matrices -> matrix k + 1 written as the world matrix of the model joint with role k (19 roles, the model's block C). So:

  • One motion fits every robo: it is retargeted through IK with each robo's own limb lengths.
  • You author rotations and IK targets, not bone positions: role joint positions always come from the robo's lengths.
  • Elbows and knees bend one way; a bend off the hinge is not possible.
  • Facing: a robo faces -Z in the points' frame, except in *_r180 motions (root rotation y + 180).
  • Root tracks and joint 0 are used by the game beyond the pose: leave them as the original has them (a +20 degree root tilt blacked the screen in a test).

5Which animation plays when (verified; full table in battle_animations.md)

The 38 slots: 0 stance, 1..9 walk / run (normal, weapon, guard, back, turned), 10 air dash, 11 double jump, 12 / 13 landing, 14..17 bomb, 18 / 19 pod, 20..25 gun, 26..29 falls, 30 magma, 31 get-up, 32 lose, 33 / 34 victory, 35 charge attack, 36 / 37 change. Per-body list: python -I tools/anim.py slots --body N.

The motion frame is not always playback time: for the timed actions the game computes it from its own counters.

AnimationMotion lengthHow it is timed
Victory (win_01 / win_02)139 framesend of battle: free battle = random of the two, team = by place, tag = win_01; holds frame 0, then plays over 140 frames (frame = 138.5 x elapsed / 140)
Lose139the same, for every loser still standing
Charge attack (cr_atk_*)60 = three 20-frame blocksthree phases; each block is stretched over that phase's duration from the body's stats (frame = 20 x (phase + elapsed / duration))
Get-up (*_powerup)2030 game frames after a knockdown (frame = 20 x elapsed / 30)
The restper motionplayed in time, 30 frames a second

Transforming bodies: their model carries an HSD joint animation; the game poses it at frame 0 normally, and during a move whose slot has flag 0x8000 at a timer that steps 1 per frame to 10 (then 9.9). Their bind pose is the other form, so exporters must apply that animation at frame 0 to show the robo form.

6Charge attack data (verified: fn_80046A68)

Per body, in the stats record (0x801C6C44 + body x 0x134):

OffsetWhat
+0xB0the charge's name (Shift-JIS, developers' name)
+0xD0per-phase flag bits (bit p = phase p; bit 3 switches which flag) - called invulnerability by the community
+0xD1per-phase bits (community: invisibility)
+0xD2..+0xD6damage / knockback (community table)
+0xD8homing: the aim turns by at most value / 1000 radians per frame (phases 0, 1)
+0xDA, +0xDC, +0xDEphase durations (frames)
+0xE0, +0xE2, +0xE4phase speeds (x 0.1)
+0xE6, +0xE8, +0xEAphase climb angles (degrees)

It also switches on an extra attack model (most likely from the body's attack_effect entry; not verified) and spawns effect / sound 0x30001.

7HSD animations (parts, transforming bodies, stages, effects)

Standard sysdolphin, as in Super Smash Bros. Melee (HSDLib reads and writes them): a model's JOBJDesc record holds {root joint, joint animation list, material animation list, shape animation list}; a joint animation is an AnimJoint tree (child, next, AObj) mirroring the joint tree; an AObj holds flags, end frame and a list of FObjs (one per channel: rotation x / y / z, scale, translation; material colour, alpha, texture ...), each a compressed keyframe stream. The game attaches the first animation of each list at load (HSD_JObjAddAnimAll) and either plays it (stages, effects) or sets its frame (fn_80095700: bodies and parts). End frames: parts 10, transforming bodies 10 (Ruhiel 9).

8Tools (this repository)

CommandWhat
python -I tools/anim.py slots --body 20a body's 38 slots: motion name, ID, length, group, flags, other bodies sharing it
python -I tools/anim.py export --body 20 --slot victory2build/anim/<name>.glb: the body's model with that motion as a glTF animation (30 fps); open in Blender
python -I tools/anim.py import --body 20 --slot victory2 IN.glb --mod MYMODthe glTF animation (on the model's JOBJ_n joints) solved back into that motion, stretched to the game's length, written to mods/MYMOD/files/motion.DBN; then python -I tools/make_mod.py mods/MYMOD builds an ISO and a shareable patch
python -I tools/crmotion.py list / export / import / roundtrip / samplethe raw format: every key as JSON and back (byte-identical)
python -I tools/crmotion_rig.py pose / gltf / import-gltfthe rig: positions of a pose, motion -> glTF, glTF -> motion
python -I tools/battle_motions.py --tsvevery body x slot as a table

How the import works: for each frame it reads the role joints' world matrices from the glTF, solves the 16 joint angles (Euler Z.Y.X, unwrapped) and the 7 IK targets backwards, keeps the replaced motion's root tracks and joint 0, then places keys greedily until every frame is within the tolerance (0.1 degree by default), with least-squares tangents. Checked: a game motion exported and imported back gives the role joints within 0.001 (Breaker's victory, 315 keys); earlier checks within 0.0034 on three robos and 0.0016 for an animation made outside the game.

Limits: motion length fixed per ID (stretch, or a main.dol change of cr_g_MotionInfo); a group's float pool of 16,384 floats (a 141-frame victory takes about 2,400; use a larger tolerance if a motion does not fit); a motion ID shared by several bodies changes on all of them; the transforming bodies' HSD animation is not part of the motion and not exported by anim.py yet.

9Code map and decompilation status (Nov 6, 2026)

Matched to C (100%; the action handlers partly as hand drafts that join the build in the next full run): cr_Motion_Play, cr_Motion_PlayFromFrame1, cr_Motion_LoadInfo, cr_Motion_UpdateBlend, cr_Chara_PoseFromMotion, fn_80095700 (set an HSD animation frame), the action handlers for victory (fn_80045868), get-up (fn_80045C08), change (fn_800459A0, fn_80045B40), double jump (fn_80048B10) and two short ones. In progress (drafts): the file register (cr_MotionFile_Register), the key sampler (cr_Motion_SampleTrack), root / points / rotations, the IK (cr_Chara_SolveArmIK / SolveLegIK / PoseLimbs), the role matrices (cr_Battle_ApplyRoleMatrices, fn_80039FAC), the action dispatcher and the remaining handlers, the end-of-battle code (fn_8004DC78, fn_8004E8D4).
