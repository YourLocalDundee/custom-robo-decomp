GameCube · GXCE01 · Custom Robo

Where everything is: animations, stages, effects, particles, scene files

One page for everything: plain explanations first (sections 1-9), then the byte-level reference for tool writers (sections 10-12). Each fact is read from the game's code (function addresses given) or counted over every file on the disc (US, GXCE01); anything not verified says so. All file names are under the disc's files/ folder (Custom Robo extracted/files/ after the one-time build). The animation byte format is in ANIMATION_GUIDE.md; deeper pages: stage_tables.md (every stage record), formats/containers.md (the archives), MODDING.md, IMPORT_EXPORT_GUIDE.md (vertices, textures, the import rules).

1Robo animations (walk, jump, shoot, victory, charge attack ...)

Stored in: logo_read_us.dbn, entry 8. Not motion.DBN (the game never reads that file).

What it is: a list of motions, each with a number (its ID, 0..1094). A motion is a set of curves for an invisible stick figure: where the hips, hands, feet and head should be, and how 16 joints turn. It does not store the robo's bones. Every frame the game bends each robo's own arms and legs to reach those points, so one motion works for every robo.

How a robo picks its animation:

  1. Each body has a list of 38 "slots" in main.dol (stance, walk, run, jump, gun, bomb, pod, falls, get-up, lose, victory 1 and 2, charge attack, ...). Each slot holds one motion ID.
  2. What the robo is doing (its action: moving, shooting, falling, winning ...) picks the slot every frame.
  3. When the slot's motion is a different one from what is playing, the game switches to it and blends from the old pose to the new one over 16 frames, so moves flow into each other.
  4. Most motions run at 30 frames a second. Victory, lose, charge attack and get-up do not: the game sets their frame from its own timers (victory waits, then plays over 140 game frames; the charge attack plays its 60 frames as three 20-frame parts, each stretched to that phase's duration).

Find it:

python -I tools/anim.py slots --body 20                  # Breaker's 38 slots: motion name, ID, length
python -I tools/anim.py export --body 20 --slot victory2 # -> build/anim/<name>.glb, open in Blender
python -I tools/battle_motions.py --tsv                   # every body x slot

3Stages

How a stage gets on screen

  1. The stage select shows the stages in the order of a list in main.dol (0x8023CF00, 40 bytes of stage ids). A stage whose record says "hidden" (+0x80 = 0) is skipped: Basic Arena (Test Use) and RPG Test.
  2. You pick one: that gives a stage id s (0..39).
  3. The game reads two entries of bg_data.BIN: 2s (the look) and 2s + 1 (the collision).
  4. It builds the look: every model, its animation, the lights and the fog. It sets up the collision.
  5. Every frame of the battle: the stage animations play (they loop), breakable parts take damage and break, moving parts carry their collision with them.

The two files of a stage

EntryWhat it holdsSize limit
2s (the look)up to 20 models; each model can carry one joint animation (moves / turns parts), one material animation (colours, fading) and one texture animation (scrolling, swapping pictures); up to 10 lights; fog0x100000 bytes
2s + 1 (the collision)one group of flat faces per model (group n = model n), then a waypoint list0x8000 bytes

In the look:

  • A model is a normal 3D model (joints, meshes, materials, textures), the same format as Melee's.
  • Its animation loops forever (every stage animation has the loop flag). Example: Basic Arena's models 2, 3 and 4 run a 720-frame loop.
  • Lights: usually two (one ambient, one directional). The first directional one also casts the robo shadows.
  • Fog: its colour also becomes the background colour behind the stage.
  • The file also has a camera, but the game never uses it (the battle camera is the game's own).
  • Do not put more than 21 meshes directly on the top joint of model 1 or later: the game freezes on load.

In the collision:

  • Each face is a flat four-cornered shape (a triangle is stored with one corner twice) with the direction it faces. Faces point toward where a robo stands: an arena's walls face inward, a box in the middle faces outward (four sides and a top, no bottom).
  • Each group has a sphere around its faces (for fast tests) and a flag word for its model:
FlagMeaning
0a normal, solid model
1..7 (bits 0-2)breakable: hit points 100 (1), 150 (2), 200 (3), 250 (4), 300 (5), 350 (6), 400 (7); when it breaks the game plays a sound / effect and the model's break animation; while hit, it flashes between its first two textures
8, 16, 24 (bits 3-4) or 32moving: the collision follows the model's animation every frame (moving platforms, rotating walls); at most 20 moving groups, 100 faces each
  • Each face also has a surface number (0 for most; other values like 8, 24, 256, 512 exist: probably ice, slopes, magma and so on; not mapped yet).
  • The waypoint list (0x284 bytes per point) is most likely the computer players' path map.

The stage record in main.dol (per stage, 0x340 bytes at 0x8020F4C8)

The US names are messages in bmg/info_usa.bin (message block 24, message = stage id). The full record is in stage_tables.md.

Two stages are alternates the menu never lists: holding one button (not identified yet) while choosing Basic Arena gives Practice Stage (id 10), and No-Man's Land (27) gives the other No-Man's Land (11).

Story-mode maps (not battle stages)

scenario_us/snr_map.BIN (94 entries) holds the story mode's walking maps: each entry is a stage model and a collision in one file (same two formats as above), plus the map's edges (x / z min and max). The objects on the maps are in scenario_us/snr_obj.BIN.

Find it and edit it

python -I tools/scene.py list stages                 # the table above, from the files
python -I tools/scene.py info stage 0                # every model, its animations, lights, fog, the collision
python -I tools/scene.py export stage 0              # -> build/scene/stage_000/: a .glb per model + the collision .obj
python -I tools/stage_collision.py info 0            # collision groups, breakable / moving flags, waypoints

To change a stage:

  1. Export it (above), or use the ready-made models_export/bg_data/bg_data_<2s>/scene_data_<n>.glb.
  2. Edit a model in Blender, then put it back: python -I tools/scene.py import stage 0 --model 3 edited.glb --mod MYMOD (several models chain: the mod's file is used as the starting point when it exists).
  3. If you added something robos should bump into, open stage_000_collision.obj (one object group_<n> per model, one face per collision face, material attr_<surface number>), add the new faces to the group of the model it stands on, facing outward (4 sides and a top), export the OBJ again with the same axes, then python -I tools/stage_collision.py import 0 edited.obj --mod MYMOD. Unchanged faces keep their bytes; new faces get the game's own normal rule (section 10). Checked: a 1.2 x 1.2 x 2.6 box on Basic Arena becomes 5 new faces in group 0, every other byte unchanged.
  4. Build: python -I tools/make_mod.py mods/MYMOD (an ISO and a patch to share).

How an effect works

  1. When a battle loads, each robo reads its gun, bomb, pod, leg and body entries into its own buffers (that is why each entry has a size limit).
  2. Each time something is fired, the game makes a new copy of the model it needs from piece 0 (a gun copies models 0 and 1 for every shot, model 2 once for the gun) and starts its animation at frame 0.
  3. The animation plays once (effect animations have no loop flag). Its keyframes move and fade the meshes, and some keyframes are particle keys: at that frame they start a particle generator (sparks, smoke, trails) at that joint.
  4. On a hit or explosion, the game copies a model from piece 1 the same way: it plays once, its particle keys fire the hit or blast particles.
  5. The charge attack copies piece 0 model 0 and piece 1 model 0 for its whole run; a robo's leg jets are 6 copies of the leg models (model 0 once, model 1 four times, model 2 once).

Each effect file also has a camera, lights and fog, but the game never reads them (only the models).

Find it:

python -I tools/scene.py list effects --kind gun   # per gun: models, meshes and particle keys of both pieces
python -I tools/scene.py info effect gun 0         # both pieces: models, animations, the particles each model fires
python -I tools/scene.py export effect gun 0       # -> build/scene/gun_effect_000/: .glb files for Blender

Ready-made exports: models_export/gun_effect/gun_effect_000_0/ (piece 0), ..._000_1/ (piece 1), and the same for bomb_effect, pod_effect, attack_effect, leg_effect.

Edit it: edit the .glb in Blender, then python -I tools/scene.py import effect gun 0 --piece 0 --model 1 edited.glb --mod MYMOD and python -I tools/make_mod.py mods/MYMOD. The entry must stay under its size limit (make_mod checks, and keeps main.dol's copy of the entry sizes in step).

5Particles

Stored in: logo_read_us.dbn, entry 0 (the boot bundle, loaded once at start). It holds 8 particle banks. Each bank is a list of particle generators (how many particles, how they move, grow, fade, which picture they use) and the pictures (textures) they use.

How they are started: only by particle keys in the effect animations above (and the common effects). A key holds a bank number and a generator number; the generator number already includes the bank (bank 6's generators are 6000, 6001, ...). Gun 0's hit, for example, fires generators 6107 and 6110.

7What a "scene" file is (scene_data)

Every stage, effect, common effect, story object and the title model is the same kind of file: a standard HSD .dat (the format Super Smash Bros. Melee uses) with one thing inside named scene_data.

The file around it

PartWhat
header (0x20 bytes)file size, data size, how many pointers, how many names
data blockeverything below (models, meshes, pictures, animations), with pointers as offsets inside the block
pointer listwhere every pointer is (so the game can turn the offsets into addresses when it loads)
namesthe name of the thing inside: always scene_data here; the game looks it up by that name

Inside scene_data: four lists

A model, piece by piece

model
 |- joint tree ............ the skeleton: every joint has a position, rotation, scale,
 |   |                      a first child and a next sibling, and maybe a mesh list
 |   '- mesh (DObj) ....... one material + one or more shapes
 |       |- material (MObj) colours (ambient, diffuse, specular), see-through amount,
 |       |    |             shininess, blending (how it mixes with what is behind)
 |       |    '- textures   pictures (TObj): the image, how it repeats, how it is
 |       |                  mapped (UVs, or reflection from the surface direction)
 |       '- shape (PObj) .. the triangles: vertex positions, normals, colours, UVs;
 |                          rigid to one joint or skinned to several
 |- joint animation ....... one entry per joint (same tree shape as the skeleton)
 |- material animation .... one entry per material: colour / fade, texture scroll, picture swaps
 '- shape animation ....... (rare) morphs

Joint flags worth knowing (a joint's flag word): 0x10 hidden, 0x80 lit by the lights, 0x200 always faces the camera (billboard), 0x4 skinned mesh, 0x20 a particle joint, 0x40000 has solid meshes, 0x80000 has see-through meshes, 0x10000000 / 0x20000000 the same for the whole tree below.

An animation, piece by piece

PartWhat
AObj (one per animated joint or material)the end frame, a loop flag (0x20000000: stages have it, effects do not), the list of tracks
track (FObj)one animated value: rotation x / y / z, position x / y / z, scale x / y / z, a colour, the alpha, a texture's scroll / scale / picture, or ptcl (fire a particle)
keys inside a trackpacked keyframes: each says how to reach the next value (jump, straight line, smooth curve with slopes) and after how many frames

Example (Basic Arena, bg_data_000.dat): model 2 is a 31-joint tree with 22 meshes; its joint animation moves 20 of the joints (rotation, position, a little scale) over 720 frames and loops; its material animation fades 16 materials over the same 720 frames.

What the game does with it

  • Stages: loads every model, attaches its animations (the first of each list), plays them every frame; loads the lights (the first directional light also gets the shadow) and the fog.
  • Effects: keeps the file in memory and makes a fresh copy of a model each time it is needed (each shot, each hit), starting its animation at frame 0; it never reads the effect's cameras, lights or fog.

Find it:

python -I tools/scene_data.py info models_dat/bg_data/bg_data_000.dat            # the lists, every model, its animations
python -I tools/scene_data.py info models_dat/bg_data/bg_data_000.dat --joints   # + every joint: flags, mesh, position
python -I tools/scene_data.py scan models_dat/gun_effect                         # one line per file of a folder

HSDRawViewer (in tools/HSDLib, Windows) opens the same files with a 3D view and a tree of every part, and exports / imports .glb for Blender. The byte offsets are in section 10 and IMPORT_EXPORT_GUIDE.md sections 3-4.

Every scene file has one root, scene_data (HSD_ArchiveGetPublicAddress(archive, "scene_data")).

scene_data (HSDLib HSD_SOBJ; checked in the game's loaders)

OffsetWhatUsed by the game
+0x00null-terminated array of model pointers (JOBJDesc)always
+0x04null-terminated array of camera descsnever
+0x08null-terminated array of lights ({LightDesc, animation list})stages only (HSD_LObjLoadDesc, at most 10)
+0x0Cfog ({FogDesc, AObj})stages only (HSD_FogLoadDesc; its colour becomes the clear colour)

A model (JOBJDesc, 0x10 bytes): root joint, then three null-terminated arrays: joint animations (AnimJoint trees), material animations (MatAnimJoint trees), shape animations. The game loads the root with HSD_JObjLoadJoint and attaches the first animation of each array (HSD_JObjAddAnimAll).

Below a joint everything is standard HSD: Joint (0x40: name, flags, child, next, DObj list or particle joint, rotation, scale, translation, inverse bind matrix, constraints), DObj (next, MObj, PObj list), MObj (render mode, TObj list, colours, pixel engine), TObj (image, palette, wrap, scale, filtering, texture matrix), PObj (vertex attributes and display list; rigid, envelope or shape animation).

An AObj holds flags (0x20000000 = loop), the end frame and a list of FObjs, one per animated channel; an FObj is a compressed keyframe stream (key opcodes CON / LIN / SPL0 / SPL / SLP / KEY, values quantised by its format byte). Channel types seen in this game: joint rotation / translation / scale x, y, z and 40 = PTCL; material ambient / diffuse / specular r, g, b, alpha; texture image swap, translation u / v, scale u / v, rotation, blend.

A PTCL key carries a 24-bit code (bytes 1-3 of the key, little-endian): bank = bits 0-5, generator = bits 6-23, a global number (bank b's generators are numbered from b x 1000). The game registers the particle callbacks at boot (cr_Particle_InitCallbacks 0x80075CA8: HSD_JObjSetSPtclCallback, HSD_JObjSetDPtclCallback, HSD_JObjSetPtclTargetCallback).

Stage build (fn_80072064, fn_80072B90, fn_80070170)

  • Every model goes into a 0x13C-byte record (lbl_8037569C + 0xB8 + n x 0x13C), at most 20. Models with any animation get flag 0x10000000 and are set to frame 0.
  • Lights: at most 10; the first with type bits 1 also gets a 600 x 440 shadow. Then the fog.
  • It hangs if a root joint of models 1 and up has more than 21 DObjs. The camera desc is never read.
  • The stage record's +0x88 (main.dol) is the model count the game uses after loading.
  • fn_80072B90 has hard-coded extras for stage ids 2, 3, 8, 9 (models 6 and 7) and 0xC: animations set to frame 0 on model 0.

Rules read from the retail data (all 3,069 quads):

  • normal = normalise((c1 - c0) x (c2 - c0)), d = -n . c0, and the normal points to where a robo stands.
  • The sphere is the corners' box centre with the farthest corner as radius (391 of 413 groups; the other 22 are a little smaller than their corners).
  • Attributes seen: 0 mostly; 8, 24, 25-28, 256, 512, 1024-2048, 1280, 5376, 197376.
