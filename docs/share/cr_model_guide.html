Custom Robo · GameCube · US (GXCE01)

Importing and exporting models

A reading guide for anyone writing an exporter or importer for robos, parts, stages and effects, in the order you meet things: from the disc down to the vertices. Each step says what is verified (read from the game's own code or checked over every file) and what is still open.

The short version

  1. Every model is HAL's sysdolphin (HSD) format, the same as Super Smash Bros. Melee. Stages and effects are plain HSD .dat files; robos and parts are HSD data behind a 0x40-byte header.
  2. Vertices land right only with three things a quick parser skips: each joint's world matrix, the fixed-point scale (frac) of every vertex attribute, and for the transforming bodies their own joint animation at frame 0.
  3. A robo body draws with one material (one texture atlas). Parts are rigid and modelled at 10× the body's scale.
  4. A stage is a model entry plus a collision entry. An effect entry holds two .dat files.
  5. A working round trip (export → Blender → import → playable ISO and a patch without game data) exists for robos, parts, stages and effects.

1Where the models are on the disc

All models sit in SFD archives (.BIN), one model per entry. The project's one-time build unpacks them and converts every model to a standard HSD .dat (1,006 models) plus glTF.

2The HSD structures you will walk

The same structures as Melee; HSDLib's layouts are right for this game. The path from a model's root joint to its triangles:

JObj (joint)     +08 child  +0C next  +10 DObj  +14 rotation xyz  +20 scale xyz
                 +2C translation xyz  +38 inverse bind matrix
 └ DObj (mesh)   +04 next  +08 MObj  +0C PObj
    ├ MObj       +04 render mode  +08 TObj chain  +0C material colours
    │  └ TObj    +04 next  +0C coordinate source  +10 rot / +1C scale / +28 translation
    │            +34 / +38 wrap S / T  +3C / +3D repeat S / T  +4C image
    │     └ Image  +00 data  +04 width  +06 height  +08 GX format (CMPR = 14)
    └ PObj       +08 vertex attribute list  +10 display list  +14 envelopes (skin weights)

Robo and part entries put a 0x40-byte header in front: word 2 points at the root joint (bodies) or at an array of root records (parts). After the HSD data come the game's own blocks: A (limb measurements), B (the material joint) and C (19 joint roles).

3Vertices: three things that make or break the shape

3a. Joint world matrices verified

A PObj without envelopes is rigid: its vertices are in the local space of the joint that owns its mesh. Build each joint's world matrix (parents first; HSD order scale, rotation, translation) and transform the vertices by it. Every part PObj is rigid. Skipping this gives the classic result where the one-joint roots look fine and the many-joint roots pile up near the origin.

Skinned PObjs (robo bodies) carry a matrix index plus up to 4 weights per vertex (0.1 steps); their vertices are in the bind pose.

3b. Fixed-point vertex formats: read frac per attribute verified

GameCube vertex components are often integers with a fixed-point shift: value = raw ÷ 2frac. The component type (u8, s8, u16, s16, f32) and frac are stored in each attribute descriptor (0x18 bytes: +0x0C type, +0x10 frac), and they differ between files and between meshes of one file. A parser that assumes one scale (÷32768 for every u16 UV) draws the frac-14 UVs at half size, and one that reads s16 as u16 wraps negative coordinates. Both look like a texture that is offset or misaligned on some robos only. TEX0 and TEX1 point at the same UV buffer on robos.

3c. Transforming bodies: apply their own animation at frame 0 verified

Four bodies carry a joint animation of their own: Defender, Seeker, Breaker (10 frames) and Ruhiel (9 frames). Their bind pose is not what the game draws. Every frame the game sets that animation to a frame:

  • frame 0 normally;
  • during a motion whose id has bit 0x8000 set (the transform moves), a value the action code steps from 0 up to 10, then holds at 9.9.

So the battle form is the body animation at frame 0, and the frames in between are the transformation. Breaker's bind pose is its other form, which matches what the export showed. Exporter rule: if the model has a joint animation, apply it at frame 0 before baking positions. The other 30 bodies have no body animation; the game poses them through 19 role joints, so their bind pose is their rest pose.

4Textures and materials

  • Format. Robo, part and almost every stage texture is CMPR (GX format 14): 8×8 tiles, each four 4×4 DXT1-style blocks (top-left, top-right, bottom-left, bottom-right), RGB565 colours big-endian, 2-bit indices most significant bit first. Alpha: when colour 0 ≤ colour 1 (as u16), index 3 is fully transparent, so CMPR carries 1-bit alpha. A decoder that drops it loses the cut-outs.
  • One material per robo body verified The draw code sets up only the block-B joint's material and draws every mesh with it, so every body is one atlas. Two texture stages: the diffuse CMPR (TEX0; the image replaces the diffuse colour) and a quarter-size grey specular mask (TEX1, blend 0.8, same UVs).
  • No texture transforms on robos and parts verified All 13,518 of their textures have identity scale, rotation and translation, repeat 1×1 and CLAMP wrap. A misplaced robo texture comes from the UV format (3b), not from a texture matrix.
  • Stages do use them. 291 of 1,414 stage textures tile, mostly the detail and environment layers (TEX1, TEX2) with REPEAT wrap and repeat 8×8, 16×2, 24×24 or 40×40. Multiply those layers' UVs by the repeat counts and the texture's scale. Some stage materials take coordinates from the normals (reflection maps) and some colour from the vertices.
  • Colour variants are separate entries with their own images; there is no palette swap.

5Robo bodies: the skeleton the game expects

  • One root joint, 51 to 69 joints. The game finds 19 role joints through paths stored after the HSD data (block C): upper body, head, two 4-joint arms, lower body, two 4-joint legs. The motion system drives those.
  • Hands and feet are IK effectors; their bind pose sits at odd places and the game moves them. Robo 0 faces +Y in Blender.
  • Size lives in the vertices. There is no per-robo scale; the root scale is overridden at run time. A body entry must stay under 0x3A000 bytes.
  • A new skeleton works with a roles file naming which joint plays each role.

A part file holds several root joints ("draw groups"). The game shows one form of each part at a time:

  • Placement: each root hangs on a body role joint (gun on one forearm, bomb on the other, pods on the upper body, legs on shins and ankles), then a per-body offset, then scale 0.1, then a per-body scale vector.
  • Part animations are poses, not clips: frame = 10 × a 0-to-1 state value (11 frames).
  • Nothing is mirrored at run time: left and right pods and legs are separate roots.

7Stages

  • Model (entry 2s): scene_data holds up to 20 models, one camera, up to 10 lights and fog. Each model is a joint tree with its first joint and material animation attached at load.
  • Collision (entry 2s+1) verified A u32 group count, offsets to group headers and to quad arrays, and an optional section C. Group n belongs to scene model n. Header: bounding sphere (x, y, z, r), quad count, model flags. Quad (0x44 bytes): 4 corners, plane normal, plane distance, a u32 surface attribute. Section C looks like a waypoint graph for computer players (not verified).
  • Limits: model entry ≤ 0x100000 bytes, collision ≤ 0x8000, and models after the first may have at most 21 meshes on their root joint (the game hangs otherwise).
  • open Spawn points, the battle camera, the meaning of the surface attributes.

8Effects (projectiles, blasts)

Each *_effect.BIN entry is a u32 count (2), count + 1 offsets, padding to 0x20, then two standard .dat files, each with a scene_data root (models, camera, lights, fog, joint and material animations) and padded to 0x20. Size limits per entry: gun 0x16000, bomb and pod 0x40000, attack 0x14000, leg 0x1000. open What the second .dat is for.

8bBattle animations: victory, lose, charge attack verified

Every body has a set of 38 motion slots. The body's entry in cr_g_BodyData points at its set (Chickenheart uses set 27 and bodies 27 to 32 use sets 28 to 33, so always follow the pointer). Motion data for all 1,095 motions is one file, entry 8 of logo_read_us.dbn. A slot holds a motion ID plus flag 0x8000, which also runs the transforming bodies' own animation.

Charge attack phases. Each phase takes its duration, speed (×0.1) and climb angle from the body's stats record (+0xDA/DC/DE, +0xE0/E2/E4, +0xE6/E8/EA), and phases 0 and 1 home on the target by up to (+0xD8)/1000 radians per frame. It also switches on an extra attack model (most likely from the body's attack_effect entry). Changing a phase's duration retimes only that phase's 20-frame block of the motion.

Replacing an animation: keep the length (win and lose 139 frames, charge attack 60, get-up 20). The game maps its own timers onto those frames, so a longer motion is cut off and a shorter one holds its last frame.

9The working round trip

Disc ISO → the one-time build → every model as a standard .dat
HSDRawViewer --export → glTF (one per root joint or scene model)
Blender, by hand or by script
HSDRawViewer --import over the original .dat: everything you did not change stays byte-identical
make_mod.py → a playable ISO and a patch with no game data, which players apply to their own ISO

One command runs all of it per category (robos, parts, stages, effects). With no edit, the round trip gives back the clean disc byte for byte for robos, all 40 stages and the effect archives.

Bring your own tool: anything that writes a standard HSD .dat plugs in. For robos and parts the project's converter rebuilds the game entry from the .dat and keeps blocks A, B and C; stage and effect .dat files go in as they are.
